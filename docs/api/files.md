# Files API

PeakCloud stores file metadata in PostgreSQL and binary objects in S3-compatible object storage.

All file endpoints require an authenticated PeakCloud session.

## Storage Model

File metadata is stored in PostgreSQL.

Binary file contents are stored in S3-compatible object storage. PeakCloud currently uses MinIO for local development.

Objects are stored under user-specific namespaces. Clients never provide or receive internal object keys.

## Authentication

All endpoints require a valid PeakCloud session cookie.

Requests without a valid session return:

    HTTP/1.1 401 Unauthorized

## Upload File

Endpoint:

    POST /api/v1/files

Content type:

    multipart/form-data

The multipart field must be named:

    file

Example:

    curl \
      -b /tmp/peakcloud-cookies.txt \
      -F "file=@report.pdf" \
      http://localhost:8080/api/v1/files

Successful response:

    HTTP/1.1 201 Created

The response contains the stored file metadata.

Uploads larger than the configured MAX_UPLOAD_SIZE_MB limit are rejected.

## List Files

Endpoint:

    GET /api/v1/files

Returns files owned by the authenticated user.

Successful response:

    HTTP/1.1 200 OK

Users cannot list files belonging to other accounts.

## Get File Metadata

Endpoint:

    GET /api/v1/files/:id

Returns metadata for a file owned by the authenticated user.

Successful response:

    HTTP/1.1 200 OK

If the file does not exist or belongs to another user:

    HTTP/1.1 404 Not Found

PeakCloud intentionally returns 404 instead of 403 so the API does not reveal whether another user's file exists.

## Download File

Endpoint:

    GET /api/v1/files/:id/download

Streams the stored object to the authenticated owner.

Successful response:

    HTTP/1.1 200 OK

The response includes Content-Type, Content-Length, and Content-Disposition headers.

If the file does not exist or belongs to another user:

    HTTP/1.1 404 Not Found

## Delete File

Endpoint:

    DELETE /api/v1/files/:id

Deletes both the object from object storage and its metadata record.

Successful response:

    HTTP/1.1 204 No Content

If the file does not exist or belongs to another user:

    HTTP/1.1 404 Not Found

## Object Keys

Object keys are generated by PeakCloud and are not based directly on user-supplied filenames.

The current layout is:

    users/{owner_id}/{year}/{month}/{uuid}

This provides user-level namespacing while preventing filename collisions.

## Security

PeakCloud enforces ownership checks on metadata retrieval, downloads, and deletion.

A user cannot access another user's files even when the other file's UUID is known.

Original filenames are validated before upload to reject empty names and path traversal attempts.

Internal object keys are not exposed through the public API.

## Consistency

When an object upload succeeds but metadata persistence fails, PeakCloud attempts to delete the uploaded object to avoid leaving orphaned storage objects.

Deletion removes the binary object and its corresponding PostgreSQL metadata.
